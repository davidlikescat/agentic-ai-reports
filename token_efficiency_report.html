토큰맥싱에서 밸류맥스로
— 에이전트 시대의 토큰 효율화 전략과 B2B AI 사업 시사점

국내 1,000여 기관이 사용하는 기업용 AI 포털 ‘웍스 AI’와 LLM 게이트웨이 ‘비즈라우터’를 운영하는 AI3 표철민 대표가 현장에서 목격한 ‘토큰맥싱’의 종료와 ‘밸류맥스’ 전환, 그리고 토큰을 줄이면서 품질을 지키는 4가지 실무 기법을 정리·분석하고, 외부 자료로 보완한 전략 보고서입니다.

작성일 2026-09-28 영상 ① 토큰맥싱 위해 좌충우돌 했던 회사들이 요즘 하는 것 (24분) 영상 ② 토큰사용 줄이면서 품질은 유지하는 4가지 방법 (25분)

0핵심 요약 (Executive Summary)

2026년 상반기를 지배했던 “일단 많이 써보자”는 토큰맥싱은 불과 몇 달 만에 “비용 대비 가치”를 따지는 밸류맥스로 전환되었다. 원인은 에이전트다. 사람이 100자를 물어도 에이전트는 MCP 도구를 여러 번 호출해 수천 자를 컨텍스트에 싣고, 직원들은 회사 돈이므로 가장 비싼 모델만 쓴다. 비용은 기하급수적으로 늘었지만 생산성 향상은 경쟁사 대비 확신하기 어려워 경영진이 속도 조절에 들어갔다.

영상②
영상이 제시하는 4가지 토큰 효율화 기법
  1. 모델 라우팅 (Smart Routing) 플래그십 모델을 쓸 필요가 거의 없다. 작업 난이도에 따라 경량 모델로 자동 분기. 단, 대화 중간 승격은 캐시를 깨뜨려 오히려 비용이 늘 수 있으므로 라우터는 “라우팅 여부” 자체도 판단해야 한다.
  2. 토큰 프루닝 (Context Pruning) 도구가 가져오는 결과물을 필요한 부분만 남기고 가지치기. 코딩 에이전트 사례에서 200줄 이상을 14줄로 줄이고도 품질이 오히려 2% 상승.
  3. 프롬프트 캐싱 (Prompt Caching) 긴 대화에서 반복되는 프리픽스를 캐시. AI3는 2026년 4월 캐싱을 공격적으로 적용해 고객 지출을 평균 20% 절감.
  4. 결정론적 도구 호출 (Deterministic Tool Calls) 도구 경로를 AI 자율에 맡기지 않고 템플릿·워크플로로 고정. 경량 LLM이 먼저 워크플로를 짜고 플래그십이 실행하거나, 파이썬 MCP가 1→2→3→4 순서로 데이터를 모아 넘기는 방식. 특정 모델의 도구 호출 폭주(한 질문에 100회)를 20회 상한으로 차단한 사례.
이 보고서의 5가지 전략적 결론 (B2B AI 사업자 관점)

① 토큰 비용은 이제 고객 이탈 요인이다 — “예산 상한 + 블랙박스” 구조를 관리해 주는 사업자가 신뢰를 얻는다. ② 효율화의 핵심 레버는 캐시다 — 실증 연구에 따르면 코딩 에이전트 비용의 약 87%가 캐시 관련 과금이며, 토큰 수 감축이 곧 비용 감축은 아니다. ③ 스마트 라우터·평가(Eval)는 게이트웨이 사업자의 차별화 기능이자 신규 수익원이다. ④ 결정론적 워크플로 + 사내 데이터 MCP가 ‘2세대 에이전트’의 표준 아키텍처다 — 데이터 레이크를 갖춘 기업이 유리하다. ⑤ 효율화로 줄어든 비용은 사용량 증가로 되돌아온다(제본스 효과) — 절감은 매출 손실이 아니라 락인 투자다.

1영상① 정리 — “토큰맥싱 위해 좌충우돌 했던 회사들이 요즘 하는 것”

기업들이 AI를 전면 도입한 후 벌어진 일, 에이전트가 토큰을 폭증시키는 구조, 토큰맥싱이 몇 달 만에 막을 내린 이유, 그리고 밸류맥스 단계에서 기업들이 실제로 하고 있는 일(경량 LLM 워크플로, 결정론적 MCP, 데이터 레이크)을 다룬다.

챕터별 흐름

  • 02:29기업에 AI를 풀어주자 벌어진 일 — 도입 의사결정엔 1년이 걸리지만, 통과되면 “일단 써봐라” 관대하게 개방. 첫 주 트래픽이 폭증했다가 급락한 뒤 “그 회사의 AI 활용 역량”으로 수렴. 업종별 편차 큼(망분리 기업·현장직 비중 높은 제조·건설은 활용률 저조, 개인 결제로 ChatGPT/Claude를 쓰던 조직은 매주 증가).
  • 05:55AI 에이전트가 토큰을 폭증시키는 이유 — “신사업 해도 돼?”라는 한 문장에 에이전트가 법제처 현행법을 뒤지고, 국가 데이터를 조회해 500~1,000자를 컨텍스트에 싣는다. 사용자는 100자만 입력했는데 입력 토큰이 폭증. 프롬프트 엔지니어링을 에이전트가 대신 하는 시대.
  • 08:11토큰맥싱이 몇 달 만에 막 내린 이유 — 6개월 전엔 회사 로비에 개발자 토큰 사용량 리더보드를 걸던 시절. 그러나 미국 기업 73%가 예산 조기 소진, 사람 100번 대화량을 에이전트가 1번에 소모. 모델 단가도 상승(비싼 플래그십 등장, 회사 돈이면 최상위 모델만 사용). 토큰맥싱 주장은 이제 ‘AI 워싱’으로 비칠 위험.
  • 12:11밸류맥스, 양에서 질로 — 토큰맥싱은 나쁘지 않았다. ‘토큰에 젖어본’ 회사만이 다음 단계로 갈 수 있다. 추상적 트렌드 강의 수요는 사라지고, 업무 프로세스를 진단해 구체적 도구로 개선을 제시하는 AX 컨설턴트·FDE형 인력이 각광. 사용 행태는 ‘대신 써주는 도구’에서 ‘에이전틱’으로(KB 부동산 시세·국토부·ERP·그룹웨어 연동, SAP 원가 자동 보고 워크플로, 공장 수율 에이전트 등).
  • 17:13토큰 낭비 잡는 경량 LLM 워크플로우 — 한화와의 사례: MCP 20개를 주고 자유 판단을 맡겼더니 경로가 매번 달라지고 토큰 낭비·일관성 저하. 해법은 경량 LLM이 먼저 워크플로를 설계하고 플래그십이 실행. 다른 고객사는 파이썬 프로그램이 순서를 강제하는 결정론적 MCP(DART→NICE 신용평가→PDF→LLM)로 해결.
  • 21:02데이터 레이크 구축 기업이 유리한 이유 — 빅데이터 열풍 때 데이터를 중앙화한 회사는 MCP 파이프만 꽂으면 된다. 반면 RAG로 일찍 시작한 1세대 AX 기업은 태생적으로 100% 정확할 수 없는 기술에 실망해 이탈. 지금은 MCP로 DB를 직접 쿼리(자연어→SQL)하므로 환각이 사실상 사라졌다 — “MCP 덕분에 꽃이 폈다”.
“사람이 100번 쓸 대화를 에이전트가 요새는 한 번 쓴대요. … 지출이 느는 속도 대비 우리 회사가 저렇게 좋아지고 있는 거야? 이게 뚜렷하게 보이지 않으니 슬로다운.”— 표철민 AI3 대표, 영상① 08:11~

핵심 메시지 해석

세대 구분이 명확해졌다

1세대 = RAG + 프롬프트(정확도 한계로 실망), 2세대 = MCP 에이전트(사내 데이터 직접 쿼리, 환각 급감). 지금 모든 한국 기업이 “좋은 두뇌(LLM) + 사내·공공 데이터 MCP → 에이전트 → 오케스트레이션/워크플로”를 동시에 만들고 있으며, 그 과정에서 발생하는 토큰 낭비·일관성 저하가 공통 과제다.

수요자가 성숙했다

불과 1~2년 만에 기업은 “에이전트로 무엇을 할 수 있는지”를 스스로 알게 됐다. 이제 원하는 것은 추상적 비전이 아니라 “당신의 프로세스를 어떤 도구로 어떻게 바꿔 얼마를 아끼는가”라는 컨설팅형 구체성이다. 교육·솔루션 사업자의 포지션이 FDE(Forward Deployed Engineer)형으로 이동 중.

2영상② 정리 — “토큰사용 줄이면서 품질은 유지하는 4가지 방법”

기업들이 1차 에이전트를 만들고 “결과물은 나왔는데 현장에서 잘 안 쓰이고, 한 번 돌리면 5,000원이 나온다”는 문제에 부딪힌 지금, AI3가 실무에서 적용 중인 4가지 기법과 스마트 라우터 구현 방식 3가지, 평가(Eval) 서비스의 부상, 그리고 AI3가 직접 겪은 토큰 비용 문제를 다룬다.

챕터별 흐름

  • 00:44토큰을 줄이고 품질을 유지하는 방법 — 초기엔 결과물이 우선이라 비싼 걸 알면서도 효율화를 생각하지 못했다. 이제 2세대 에이전트를 만들며 “모든 모델의 수준이 올라와 플래그십을 쓸 필요가 거의 없다”는 것을 확인. 오픈소스 경량 모델에 MCP로 사내 데이터를 잘 실어주면 비싼 클로즈드 모델에 꿀리지 않는다. “서울–대전–대구–부산 경로 정보만 잘 주면 경량 모델도 부산에 간다.”
  • 04:43① 모델 라우팅 — 쉬운 서브태스크·가벼운 리서치는 경량 모델로 자동 분기. 비용 통제보다 AX 우선이었던 기조 때문에 직원들이 최상위 모델만 써왔던 관행을 바꾸는 것.
  • 07:00② 토큰 프루닝 — 금감원 DART API처럼 ‘AI 시대 이전에 만들어진 API’는 분기 공시 전체를 통으로 반환한다. 필요한 건 “삼성전자 최근 3개월 지분 변동”뿐. 도구 결과를 실어주기 전에 정확히 그것만 남겨야 한다. Claude Code의 grep 도구가 가져온 200줄 이상을 14줄로 프루닝해도 결과 품질이 2% 상승한 논문 사례. 긴 컨텍스트에서 중간 부분 성능이 떨어지는 ‘lost in the middle’ 현상과 연결.
  • 09:25③ 프롬프트 캐싱 — 레시피 에이전트처럼 도구 호출이 많은 티키타카 대화에서 캐시를 잘 쓰면 대화가 길어져도 비용이 10분의 1. 단, 스마트 라우터가 매 턴 라우팅해 중간에 플래그십으로 승격하면 지금까지의 대화 전체가 새 모델의 입력 토큰으로 들어가 캐시 쓰기 할증(1.25배)을 내고, 결과적으로 처음부터 플래그십을 쓴 것보다 비싸질 수 있다. 라우터는 “캐시를 유지할 수 있는가, 캐시 재작성 비용 대비 가치 있는 라우팅인가”를 함께 판단해야 한다.
  • 11:50④ 결정론적 도구 호출 — 도구 호출을 AI에 맡기면 네이버→야후→DART 순으로 헤맨다. 손발이 많다는 정보를 일부러 차단하고 “이런 문제는 이 경로”라는 템플릿을 주는 것이 토큰 절약 전략.
  • 14:52스마트 라우터 구현 3가지 방식 — (a) 경량 LLM이 판별: 만들기 쉽지만 매 발화마다 비용·지연 발생. (b) BERT류 분류기: 매우 빠르지만 새 모델이 나올 때마다 재학습 필요(설정 파일로 완화하는 프로젝트 존재). (c) 정규식·택소노미 룰: AI 미사용으로 가장 빠르며 특정 언어·산업·코딩 전용이면 유리. 비즈라우터는 정규식 → 택소노미 → LLM 폴백 순으로 진화했고 고객이 선택 가능.

3토큰 효율화 심층 분석 — 영상 내용의 구조화와 보강

두 영상은 하나의 스토리다. 영상①이 “왜 토큰 비용이 폭증했는가(문제)”를, 영상②가 “어떻게 줄이는가(해법)”를 다룬다. 이 장에서는 토큰이 어디서 발생하는지 비용 구조를 먼저 분해한 뒤, 4가지 기법을 각각 심화하고 외부 자료로 검증·보완한다.

3.1 에이전트 토큰 비용의 해부 — 비용은 어디서 새는가

단일 채팅에서는 “사용자 입력 + 시스템 프롬프트 → 출력” 구조였지만, 에이전트에서는 한 요청이 여러 턴의 루프로 확장된다. 영상①이 지적하듯 사용자가 100자를 입력해도 (a) 에이전트가 프롬프트를 풍성화하고, (b) 연결된 도구(MCP) 정의를 모두 컨텍스트에 싣고, (c) 도구를 호출해 결과를 통째로 실으며, (d) 매 턴마다 이전 대화 전체가 입력 토큰으로 재전송된다. 비용 폭증의 진짜 원인은 (b)·(c)·(d)의 곱셈 구조다.

고정비시스템 프롬프트·도구 정의MCP 서버 7개만 연결해도 약 67K 토큰이 질문 전에 소모된다는 측정 사례. 매 턴 반복.
변동비 ①도구 결과(Tool Output)DART 분기 공시 전체, grep 200줄 등 “AI 이전 API”의 통 반환. 프루닝의 대상.
변동비 ②대화 이력 재전송턴 수 × 누적 길이. 캐시가 없으면 N턴 대화는 O(N²) 토큰. 캐싱의 대상.
변동비 ③루프 횟수도구 호출 경로가 비결정적이면 헤매는 만큼 턴이 늘어남(100회 호출 버그). 결정론적 도구 호출·상한의 대상.
단가모델 선택같은 토큰이라도 플래그십은 경량 대비 수십 배. 라우팅의 대상.

이 분해가 중요한 이유는, 4가지 기법이 서로 다른 항을 공략하며 상호작용하기 때문이다. 영상②의 핵심 통찰 — “라우팅으로 모델을 바꾸면 캐시가 깨진다” — 는 ‘단가’ 항을 줄이려다 ‘대화 이력 재전송’ 항을 폭발시키는 상호작용의 대표 사례다.

3.2 ① 모델 라우팅 — “두뇌는 이미 충분히 좋다”

영상② 표 대표의 실험은 오픈소스 경량 모델(노트북에서 구동 가능한 수준)에 사내 데이터를 MCP로 실어주면 클로즈드 플래그십과 결과가 “꿀리지 않는다”는 것이었다. 즉 품질의 결정 변수가 모델 지능 → 컨텍스트 품질로 이동했다. 이는 라우팅의 전제조건이다: 컨텍스트가 좋아야 경량 모델로 내려보낼 수 있다.

보완 학계·오픈소스에서도 같은 결론이다. LMSYS의 RouteLLM은 선호도 데이터로 학습한 라우터(행렬분해·BERT 분류기·Causal LLM 등)로 MT-Bench에서 GPT-4 성능의 95%를 유지하며 비용을 최대 85% 절감했다고 보고한다. 영상이 말한 “품질은 극히 조금, 비용은 10~15분의 1”과 정합적이다.

구현 방식속도·지연비용유지보수적합한 경우
경량 LLM 판별 (‘말하는 모자’)지연 발생(짧지만 매 발화)매 발화에 경량 LLM 요금가장 쉬움, 프롬프트만 수정도메인이 넓고 빠르게 시작해야 할 때

라우팅의 함정 — 반드시 설계에 반영해야 할 3가지

(1) 세션 단위 라우팅. 발화 단위로 매 턴 라우팅하면 중간 승격 시 캐시가 깨져 “처음부터 플래그십을 쓴 것보다 비싸진다”. 라우터는 (승격으로 얻는 품질 이득) vs (캐시 재작성 비용 + 컨텍스트 재전송 비용)을 비교해 라우팅 여부를 결정해야 한다. 실무적으로는 첫 발화에서 세션 전체의 티어를 정하고, 승격은 예외 처리하는 것이 안전하다.
(2) 라우팅 결과의 투명성. 비즈라우터처럼 “어떤 발화가 어디로 라우팅됐고, 최상위 모델만 썼을 때 대비 얼마를 아꼈으며, 백테스트로 품질이 얼마나 변했는지”를 고객에게 보여주지 않으면 라우팅은 ‘몰래 싼 모델 쓰기’로 오해받는다.
(3) 모델별 행동 특성 가드. 특정 경량 모델의 도구 호출 폭주(1질문 100회) 사례처럼, 라우팅 대상 모델별로 도구 호출 상한·최대 턴 수·예산 상한(per-request budget)을 설정하는 것이 라우터의 책임 범위에 들어간다.

3.3 ② 토큰 프루닝 — 컨텍스트는 적을수록 좋을 수 있다

영상② 프루닝의 논리는 두 겹이다. 첫째, 비용: 도구가 통으로 반환한 결과 중 실제로 필요한 것은 일부다. 둘째, 품질: 긴 컨텍스트의 중간 부분을 모델이 잘 보지 못하는 현상(lost in the middle) 때문에 불필요한 정보를 빼면 오히려 답이 좋아질 수 있다. 영상은 코딩 에이전트에서 grep 결과 200여 줄을 14줄로 줄이고 품질이 2% 오른 논문을 인용했다.

보완 2026년 5월 공개된 LaMR(Context Pruning for Coding Agents via Multi-Rubric Latent Reasoning)은 SWE-Pruner 코퍼스 6.1만 건으로 학습한 프루너가 다중 턴 에이전트 작업에서 토큰을 최대 31% 추가 절감하면서 단일 턴 Exact Match를 최대 +3.5 개선했고, 16개 다중 턴 비교 중 12개에서 무프루닝 전체 컨텍스트를 이겼다고 보고한다. 프루닝은 “의미적 관련성”과 “구조적 필수성(import·클래스 헤더 등)”을 따로 판단해야 한다는 점이 실무 시사점이다 — 무작정 잘라내면 코드가 깨진다.

프루닝을 어디에 넣을 것인가 — 3개 삽입 지점

도구 설계 단계(가장 효과적): MCP가 DB 테이블 전체가 아니라 필요한 행만, 제목·메타데이터를 보고 필요한 문서만 가져오도록 설계. 영상②가 “각각의 도구를 잘 설계하는 것이 지금 너무너무 중요한 화두”라고 강조한 지점. 한 에이전트 실행에 5회 도구 호출이 있고 각 호출을 1/N로 줄이면 절감은 곱으로 누적된다.
도구 결과 후처리 단계: 도구 결과를 컨텍스트에 싣기 전에 경량 모델·규칙·학습된 프루너가 요약·발췌. 비즈라우터 같은 게이트웨이가 개입할 수 있는 지점.
대화 이력 단계: 오래된 턴을 요약으로 대체(컴팩션). 단, 캐시 프리픽스를 바꾸므로 캐시와의 상호작용을 고려해야 한다(3.5 참조).

3.4 ③ 프롬프트 캐싱 — 가장 큰 레버, 가장 깨지기 쉬운 레버

영상② AI3가 2026년 4월 캐싱을 전면 적용해 고객 지출이 평균 20% 즉시 감소한 것은 캐싱이 단일 기법으로 가장 큰 효과를 낸다는 증거다. 동시에 “대화가 길어져도 10분의 1”이라는 설명은 캐시 읽기 단가가 기본 입력 단가의 10분의 1 수준이라는 주요 모델사의 가격 구조를 반영한다.

보완 공식 문서 기준 Anthropic의 캐시 가격 구조는 다음과 같다. 5분 캐시 쓰기 1.25배, 1시간 캐시 쓰기 2배, 캐시 읽기 0.1배(최신 모델은 0.025~0.05배까지 하락). 캐시는 tools → system → messages 계층으로 작동하며, 상위 계층이 바뀌면 하위 전체가 무효화된다. 즉 도구 정의를 바꾸거나 모델을 바꾸면 캐시 전체가 깨진다 — 영상②가 경고한 “라우팅 승격 시 캐시 라이트” 현상의 기술적 근거다.

캐시 친화적 아키텍처 원칙 (실무 체크리스트)
  1. 정적 콘텐츠를 앞에, 동적 콘텐츠를 뒤에. 도구 정의·시스템 프롬프트·사내 지식(정적) → 대화 이력 → 타임스탬프·사용자 질의(동적). 브레이크포인트를 동적 콘텐츠에 걸면 캐시 적중률 0.
  2. 도구 정의를 안정화. 세션 중 도구 추가·삭제·순서 변경은 전체 캐시를 깨뜨린다. 도구 세트는 세션 시작 시 확정하고, 필요 시 ‘도구 검색(Tool Search)’ 패턴으로 지연 로딩.
  3. 세션 단위 모델 고정. 라우팅은 세션 시작 시 결정. 중간 승격은 캐시 재작성 비용을 명시적으로 계산한 뒤 예외적으로 허용.
  4. TTL 관리. 5분 TTL은 요청 시작 시점 기준. 사람이 읽고 답하는 티키타카 대화는 5분을 넘기기 쉬우므로, 고빈도 워크로드는 1시간 TTL(2배 쓰기)의 손익분기를 계산.
  5. 캐시 지표를 청구서에 노출. cache_read / cache_creation / input 토큰을 고객 대시보드에 분리 표시해 “왜 20% 줄었는지”를 설명 가능하게.

3.5 ④ 결정론적 도구 호출 — 자율성을 줄여 일관성과 비용을 얻는다

영상① 영상② 두 영상을 관통하는 가장 실무적인 교훈이다. MCP 20개를 주고 플래그십에 자유 판단을 맡기면 경로가 매번 달라지고(블랙박스), 토큰이 낭비되며, 결과 일관성이 떨어진다. 현장에서 검증된 두 가지 패턴은 다음과 같다.

패턴 A — 플래너/실행자 분리 (한화 사례)

경량 LLM에 “사용자 요청 + 보유 도구 목록 + 원하는 결과물 형태”를 주고 워크플로를 먼저 설계하게 한다. 플래그십은 그 워크플로만 받아 실행한다. 비싼 모델이 탐색에 토큰을 쓰지 않으므로 일관성과 비용이 동시에 개선된다.

패턴 B — 결정론적 MCP (투자 의사결정 에이전트 사례)

파이썬 프로그램이 ① DART 조회 → ② NICE 신용평가 조회 → ③ PDF 생성 → ④ LLM 전달을 고정 순서로 수행한 뒤 결과만 LLM에 넘긴다. AI는 ④ 이후의 판단에만 개입한다. 반복 업무·규제 보고처럼 경로가 정해진 업무에 적합.

보완 이 방향은 글로벌 모델사의 최신 패턴과도 일치한다. Anthropic의 ‘Tool Search(점진적 공개)’는 도구 스키마를 미리 싣지 않고 필요 시 검색해 도구 정의 토큰을 약 85% 줄이면서 MCP 평가 정확도를 오히려 높였다고 알려져 있고, ‘Code Execution with MCP’는 MCP 서버를 코드 API로 노출해 에이전트가 샌드박스에서 도구를 체이닝하게 함으로써 15만 토큰 → 2천 토큰(98.7% 절감)을 제시했다. Cloudflare의 ‘Code Mode’ 역시 2,500개 엔드포인트의 도구 카탈로그(117만 토큰)를 타입 SDK로 대체해 약 1천 토큰으로 줄였다. 공통점은 “LLM이 도구 사이를 오가며 중간 결과를 컨텍스트에 싣게 하지 말고, 코드(결정론)가 데이터를 모아 최종 결과만 넘기게 하라”는 것이다 — 영상①의 패턴 B와 정확히 같은 철학이다.

중요한 반론 — “토큰 감축 ≠ 비용 감축”

2026년 7월 arXiv에 공개된 실증 연구(“Token Reduction Is Not Cost Reduction”)는 API 기반 코딩 에이전트에서 2,908쌍의 실행을 모델사 청구 기준으로 측정한 결과, 가장 공격적인 도구 출력 압축이 토큰을 38.4% 줄였지만 청구 비용은 6.8% 증가했다고 보고한다. 원인은 세 가지다: (1) 재구성된 비용의 약 87%가 캐시 생성·읽기 과금이라 도구 출력 토큰은 애초에 청구서의 작은 부분이고, (2) 압축으로 필요한 정보가 빠지면 모델이 다시 검색·재읽기를 해 턴이 늘어나며 프리픽스 전체가 재전송되고, (3) 압축된 출력이 후속 도구(셸 파이프, 편집 앵커)를 깨뜨려 폴백이 발생한다. 토큰 감축량과 비용 변화의 상관은 r=0.15에 불과했다.

시사점: 영상②의 4가지 기법은 캐시를 중심에 두고 통합 설계해야 한다. 프루닝은 캐시 프리픽스를 바꾸지 않는 위치(도구 설계 단계)에 우선 적용하고, 효율화 성과는 토큰 수가 아니라 “과업 성공률로 보정한 end-to-end 청구 비용”으로 측정해야 한다. 이는 영상②가 강조한 Eval의 필요성을 비용 측면에서 재확인한다.

4.2 효율화의 역설 — 절감은 사용량으로 되돌아온다

AI3가 캐싱으로 지출을 20% 줄였더니 1~2개월 뒤 사용량이 회복·증가한 현상은 에너지 경제학의 제본스 역설과 같다. 단가가 내려가면 한계 사용이 늘어난다. 글로벌 데이터(단가 -98%, 청구액 +320%)도 같은 방향이다. 사업자에게 이것은 두 가지를 의미한다. 첫째, 효율화는 매출을 줄이는 것이 아니라 고객의 예산 상한 안에서 사용량 성장의 여지를 만드는 것이다. 둘째, 효율화 없이 방치하면 고객은 상한을 넘는 순간 이탈하거나 프로젝트를 접는다 — 표 대표가 “고객이 스트레스를 받지 않게 하는 것이 모든 AI 프로바이더에게 중요한 인사이트”라고 말한 배경이다.

5전략적 인사이트 — 국내 B2B AI 사업자(통신사·플랫폼 사업자) 관점

AI3는 “모델사와 고객 사이에서 대신 고민해 주는 존재”로 스스로를 재정의했다. 예전엔 ‘API 래퍼’라는 자조가 있었지만, 토큰 경제가 블랙박스가 된 지금 그 중간자의 가치는 오히려 커졌다. 이는 AICC·AX 플랫폼·소버린 클라우드를 묶어 B2B AI를 사업화하는 통신 사업자에게 직접적인 시사점을 준다.

인사이트 1 — ‘토큰 FinOps’가 B2B AI 플랫폼의 핵심 기능이 된다

고객의 진짜 불안은 “원가는 정해져 있는데, 에이전트가 얼마나 쓸지 모른다”는 예측 불가능성이다. 종량제 위에 (a) 부서·에이전트·프로젝트별 예산 한도, (b) 도구 호출·턴·요청당 비용 상한, (c) 캐시 적중률·라우팅 분포·절감액이 보이는 대시보드, (d) 이상 사용 실시간 알림을 기본 탑재한 플랫폼은 “쓸수록 두려운 AI”를 “쓸수록 안심되는 AI”로 바꾼다. FinOps 팀의 98%가 AI 지출을 관리하기 시작한 지금, 이 기능은 옵션이 아니라 계약 조건이 되어 간다. 특히 예산이 연 단위로 확정되는 대기업·공공 고객에게는 예산 보장형(capped) 요금제와 결합할 때 강력한 차별화가 된다.

인사이트 2 — LLM 게이트웨이의 스마트 라우터는 ‘멀티모델 + 국산모델’ 전략의 실행 엔진이다

영상②의 핵심은 “두뇌는 이미 충분하다, 컨텍스트가 품질을 결정한다”이다. 이는 소버린 AI 관점에서 중요한 함의를 갖는다. 경량·오픈소스·국산 모델이 사내 데이터 MCP와 결합하면 플래그십 대비 손색이 없다는 관찰은, 라우터가 비용뿐 아니라 데이터 주권·망분리 요건에 따라 모델을 분기하는 정책 엔진이 될 수 있음을 뜻한다. 예컨대 “사내 문서 포함 요청 → 국산·프라이빗 모델, 공개 정보 요청 → 글로벌 경량 모델, 고난도 추론 → 플래그십(세션 고정)”의 3단 라우팅이다. 망분리 기업의 활용률이 낮다는 영상①의 관찰은 곧 내부망에서 동작하는 게이트웨이+경량 모델 조합의 미충족 수요를 가리킨다.

인사이트 3 — Eval-as-a-Service는 컨설팅과 플랫폼을 잇는 신규 수익원이다

한국 기업들은 1차 에이전트를 만들었지만 ‘깎기’ 단계로 못 가고 있고, 그 깎기는 담당자에게 귀찮은 일이다. “당신의 에이전트를 주면 모델·프롬프트·컨텍스트·MCP·워크플로 변수를 바꿔가며 실험해 성공당 비용을 30% 낮추는 구성을 보고서로 드린다”는 서비스는 (a) 플랫폼에 올라온 에이전트를 대상으로 자동화가 가능하고, (b) 결과가 곧 라우팅·캐싱 설정으로 이어져 플랫폼 락인을 강화하며, (c) 영상①이 말한 FDE형 컨설팅 수요와 정확히 맞물린다. 미국에서는 YC 투자를 받은 스타트업이 다수지만 한국엔 아직 없다 — 선점 가능한 공백이다.

인사이트 4 — AICC·버티컬 에이전트는 ‘결정론적 워크플로 우선’으로 설계해야 한다

컨택센터·금융·공공 업무는 경로가 정해진 반복 과업이 대부분이다. 영상①의 패턴 B(파이썬 MCP가 순서를 강제하고 LLM은 최종 판단만)와 패턴 A(경량 플래너 → 플래그십 실행자)는 이런 도메인에서 토큰 절감·일관성·감사 가능성(설명 가능성)을 동시에 준다. 특히 AICC처럼 동시 세션이 수만 건인 워크로드에서는 비결정적 탐색 1회의 비용이 곱해지므로, 자율 에이전트는 예외 처리 구간에만, 정형 구간은 결정론적 워크플로로라는 설계 원칙이 P&L을 좌우한다. 더불어 콜 단위 세션은 캐시 TTL(5분) 안에 자연스럽게 들어오므로 시스템 프롬프트·상담 지식 베이스를 캐시 프리픽스로 고정하면 캐싱 효과가 가장 크게 나타나는 워크로드다.

인사이트 5 — 데이터 레이크·MCP 파이프라인이 AX 사업의 진입 지점이다

“데이터 레이크를 구축한 회사는 MCP 파이프만 꽂으면 된다”는 관찰은 AX 사업의 첫 단추가 모델이 아니라 사내 데이터의 MCP화임을 말한다. 사내 데이터 MCP 개발은 IT 부서의 일이고, 에이전트 설계는 현업의 일이며, 시스템화는 다시 IT를 거친다. 이 3자 협업을 표준화한 ‘사내 데이터 MCP 구축 + 결정론적 워크플로 템플릿 + 토큰 FinOps 대시보드’ 패키지는 RAG에 실망하고 이탈한 1세대 AX 기업을 다시 불러올 수 있는 재진입 상품이 된다. 좁게 설계된 MCP(전체 테이블이 아니라 필요한 행만)는 그 자체가 프루닝이므로, 데이터 파이프라인 품질이 곧 토큰 효율이다.

인사이트 6 — “모델사도 베타다”: 모델 행동 리스크를 흡수하는 중간자 가치

특정 모델의 도구 호출 100회 버그를 고객 신고로 발견하고 20회 상한 패치와 환불로 대응한 사례는, 모델사가 빠르게 모델을 갈아치우는 환경에서 모델별 행동 특성을 관측하고 가드레일을 운영하는 것이 플랫폼 사업자의 핵심 역량임을 보여준다. 한 고객사의 문제를 고치면 나머지 999개 고객이 함께 혜택을 보는 구조(네트워크 효과)이며, 이는 다수 고객을 보유한 사업자일수록 유리하다. 모델 버전 변경 시 회귀 테스트(golden set 백테스트)와 캐시 무효화 영향 분석을 릴리스 절차에 포함해야 한다.

종합 — 밸류맥스 시대 B2B AI 사업자의 가치 방정식

고객 가치 = (과업 성공률 × 사용량) ÷ (예산 상한 내 예측 가능한 비용). 토큰맥싱 시대에는 분자만 키웠고, 밸류맥스 시대에는 분모를 예측 가능하게 만드는 자가 이긴다. 영상의 4가지 기법(라우팅·프루닝·캐싱·결정론적 도구 호출)은 분모를 줄이는 기술이고, Eval은 분자와 분모를 동시에 재는 계측기이며, 사내 데이터 MCP는 분자를 키우는 기반이다. 세 가지를 하나의 플랫폼 계약 안에 묶는 것이 사업 전략의 골자다.
